## 现状问题（诊断，2026-09-23）

「单个相位执行后中断，应给用户提示可执行操作，但现在不稳定」的结构性根源：

1. **exec 不校验执行位置**——`--task/--phase` 与 `state.currentStage` 无一致性检查，agent 可 exec 任意任务任意相位；state 表达的「当前位置」与实际喂给 AI 的 prompt 可能脱节。
2. **next 调用靠约定**——相位执行完是否调 next 由 SKILL 指令约束（L1），漏调/晚调时 state 落后于现实，中断后无法从 state 可信恢复「接下来能做什么」。
3. **确认门活在 prompt 文本里**——human 相位在 state 中只有 `status: waiting-human` 一个布尔级表达；「用户要确认什么、有哪些可执行操作」没有结构化数据，提示全靠 agent 现场发挥。

## 需求输入（2026-09-23，用户方案思路）

1. **节律强制**：原子任务单相位执行后必须调用 `next`；next 执行时在 `.state.json` 中执行检查。
2. **确认标记前置生成**：若原子任务用于确认（human 相位），进入该相位的上一轮推进（next / run start）应在 state 中生成对应的**确认标记**，标记当前相位是否需要用户侧动作。
3. **操作参数注册 + 职责解耦**：`.state.json` 为阶段注册对应的操作参数。确认门与原子任务解耦：
   - 原子任务只负责**注册**确认门（声明式——现有 `phases[].type: human` + `@interact` 标记即注册源）；
   - 原子任务**不负责拦截**；
   - CLI 执行函数负责**检查拦截**，并保证确认门**可读**（任何消费方都能从 state 结构化读到，不依赖 prompt 文本）。
4. **新概念：原子上下文窗口**——通过命令规范上下文窗口内哪些内容是绑定的（含义待澄清，Q4）。

## 已确认决策（2026-09-23 评审）

| # | 决策 | 依据 |
|---|---|---|
| D1 | **门关闭通道：agent 呈现、用户选择、agent 代跑**——agent 把门注册的操作清单（命令 + 后续动作）用宿主提问工具呈现给用户，用户选择后由 agent 执行对应命令；**用户不手动执行脚本命令**。CLI 拦截保证「门未关就不能推进」，决议记入 state 留痕（强度：结构上拦住「不问就推」，不防 agent 伪造决议——呈现协议是 SKILL 级约束 + 留痕审计；严格用户亲跑通道留作后续可选） | 用户定版（Q1） |
| D2 | **门与操作参数落点：`stages[k].gate` 内嵌**——与 status 同居一处，随阶段生命周期（物化/推进/回滚同址）；对 02 基线为最小扩展 | 用户定版（Q2） |
| D3 | **提示来源 = 门注册的 operations + 派生操作**——「给用户返回可以选择哪些指令」的数据从 state 结构化读出：推进命令开门时回显，`status` 命令随时重读（中断恢复入口）；agent 转述而非发挥 | Q3 澄清后定（由 D1 通道推导） |
| D4 | **两层归属**：哪些相位需要用户确认 = **原子任务属性**（`phases[].type: "human"`，05 已有，即注册源）；流程中哪些阶段有确认门 + **支持的命令及命令对应的后续动作 = 注册进 `.state.json`**（进入 human 相位的推进命令写入） | 用户定版（Q4 补充） |
| D5 | **节律强制 = 结构锁**：exec/validate 校验执行位置 ∈ currentStage；next 在门未关闭时拒绝推进——「强制单相位后调 next」不靠指令约定，靠位置拦截锁死（不 next 则永远停在原相位） | 需求输入推导（方案思路 1/3） |
| D6 | **门操作集 = 任务级定制三元组**（参数 name / 描述 desc / 动作 action），声明于 `phases[].gate.options`；未声明时 CLI 标准二元兜底（approve/reject）。动作分推进型（next，可喂 `next --decision`）与转移型（rollback/finish，直接执行） | 用户定版（P1 评审） |
