## 已确认决策

| # | 决策 | 依据 |
|---|---|---|
| D1 | **命令哲学：命令即语义操作**——每个命令封装自己的状态变更；不设通用 `update`（避免调用方理解并手工拼装状态机） | 用户定版 |
| D2 | `run start` **移交「workflow 预设与动态组装」设计轮**：start 需动态组装/使用预设 workflow 并动态生成 stages，该前置依赖尚未设计，本轮只登记依赖关系；存档版 `--stages` 显式传入**不正式化** | 用户定版 |
| D3 | 状态修改由语义命令承担：`next`（推进）、`rollback`（回退）等各自修改 `.state.json` 执行对应逻辑 | 用户定版 |
| D4 | **`exec` 命令**：执行对应原子任务，产出**组装好的 prompt** 动态喂给 AI。prompt 组装能力随下一轮原子任务改造支持，本轮仅定义命令契约 | 用户定版 |
| D5 | `run show` / `list active` / `list history` 不进基本集（等真实需求轮再登记）——**08 轮部分落地**：断点重续真实需求到达，`list active`+`run show` 合并为顶层动词 `resume`（发现层清单 + `--run-id` 完整视图）；`list history` 仍悬置 | 用户定版（沿用 03 收敛结论；08 修订） |
| D6 | `run finish` 保留于基本集（生命周期闭环唯一入口，不依赖未设计机制） | 用户确认（P5） |
| D7 | **命名空间政策**（沉淀于 03 plan §3.4）：对象操作用两段式 `<域> <动词>`；执行原语用单段顶层动词；顶层动词所需的框架分发扩展随本轮命令登记落地 | 用户定版（2026-09-22） |
| D8 | **exec 终态输出为裸 prompt 文本**（非 JSON 包装）——四通道契约的唯一例外，消费者是 AI 会话本身 | 用户定版（P2） |
| D9 | **`next` 移交「原子任务改造」轮**：推进语义与原子任务执行模型强耦合，本轮无法拍板 | 用户定版（P3） |
| D10 | **rollback 语义**：每次执行回滚指定的一个阶段；按 DAG 逻辑只重置「目标→当前」路径上的节点（并行分支不动）；回滚清理的文档归档到 `_del/` 保留历史，每次回滚独立子目录隔离（多次回滚并存） | 用户定版（P4） |
| D11 | 本轮登记集合 = `run finish` + `rollback`（状态回滚部分）；rollback 文档归档实现随产物机制，契约先行 | 由 D9/D10 推出 |

## 架构原则：渐进式加载（D4 的依据）

> AI 每次只读**必须的**上下文，不全量加载。exec 输出组装好的 prompt，保证喂给 AI 的内容恰好是当前原子任务所需——上下文的「选择权」从 agent 手里移到流水线手里。

这也是 v2 对「AI 上下文失控」问题的结构性回答（承接历史 issue #1 渐进式上下文加载、#45 Prompt 读取保障的命题）。

## 范围

**本轮**：

- 契约定义：`run finish` / `rollback` / `exec`（`next` 与 `run start` 已移交）
- 登记进 `tools/cli.js` 注册表：`run finish` + `rollback`（状态回滚部分；文档归档实现待产物机制）
- 顶层动词所需的框架分发扩展（随 rollback 登记落地）

**不在本轮**：
- `run start`（移交预设组装轮）、`next`（移交原子任务改造轮）
- `exec` 的 prompt 组装实现（下一轮随原子任务改造）
- rollback 的文档归档实现（随产物登记机制；契约已定）
- 确认门/人审相位的状态转换细节（`waiting-human` 等的进入与离开——属执行循环设计轮）
- 产物机制的任何部分
