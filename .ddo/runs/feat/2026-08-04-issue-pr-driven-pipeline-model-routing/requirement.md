# 用户需求

> 用户触发此流水线的原始需求描述。

## 原始需求

# Issue/PR 驱动开发流水线 + 节点级模型路由 —— 设计交接文档

- 关联需求：Issue 原子任务能力支持（issue 拉取/创建/提交）
- 文档性质：交接用设计文档。只讲设计思路与参考解法，不涉及具体文件与改动清单。
- 阅读对象：接手实施该能力的工程师 / agent。

---

## 1. 背景与目标

现状：本流水线是"指令型 runtime"——执行 agent 即引擎，文件系统加运行状态文件即状态机。run 由"会话内的一句自然语言需求"触发，确认靠本地对话，模型固定为会话模型。

本次要交付两项相互独立、可并行的能力：

- **能力 A：Issue/PR 驱动工作流。** 把触发、审核、状态、交付全部搬到 GitHub Issue/PR 上，本地 worktree 只负责执行。目标是异步、可审计、human-in-the-loop 但不绑定会话。
- **能力 B：节点级模型路由。** 让不同原子任务使用不同模型，按节点分配成本与能力（规划用强推理、机械任务用轻模型、评审用多模型交叉）。

交汇点：能力 A 的 coding 与 review 节点，直接消费能力 B 的模型路由。

---

## 2. 总体架构

核心思想：**控制平面与执行平面分离**。

- **控制平面 = GitHub。** label 是状态机，comment 是审计与反馈数据，PR 是交付物。
- **执行平面 = 本地 git worktree。** 隔离执行，运行状态持久化在 run 状态文件里。
- **桥梁 = gh CLI。** 双向读写 issue 与 PR。

必须坚守的一条设计原则：

> 流水线的正确性不依赖任何常驻进程。所有状态都落在"文件系统 + GitHub"两处，任何会话随时可恢复。轮询与监听只是降低延迟的加速器，不是正确性来源。

这条原则决定了后面所有机制的形态：不建守护进程、不建服务器，一切以"可中断、可恢复、可重入"为前提。

## 3. 能力 A：Issue/PR 驱动工作流

### 3.1 控制信号的选择：label，而非 comment

**问题**：用什么承载"触发""审核通过""否决"这类控制信号？

**思路**：控制信号必须解决授权问题——谁有资格触发流水线、谁有资格批准一个阶段。comment 任何有仓库读权限的人都能发，无法授权；而打 label 在 GitHub 上需要 triage 及以上权限，权限模型天然内置。

**参考解法**：
- 控制信号一律用 label。定义一套固定词汇，覆盖触发、认领、审核、否决、终态、挂起等状态，例如"触发""执行中""待审核:<阶段>""已批准""要求修改""失败""完成""已挂起"。
- comment 只作为数据载荷与审计记录：需求补充、否决反馈、进度播报、PR 链接。
- 由此得到一条硬规则：**流水线只执行 label 表达的控制语义，绝不执行 comment 中的任何指令**。这是防注入的底线。

### 3.2 触发与认领

**问题**：AI 如何知道"该开发这个 issue"？如何防止两个会话抢同一个 issue？

**思路**：不建后台监听。把"认领"做成一个显式原子任务，用 label 充当幂等锁——谁先打上"执行中"，谁就拥有这个 issue。

**参考解法**：
- 约定一个触发 label。人或 AI 把它打到某个 issue 上，表示"待开发"。
- 用一个"认领"原子任务承接：解析输入里的 issue 引用（编号或链接），拉取 issue 内容，**先打"执行中" label 再开始任何工作**。打 label 这一步就是认领锁。
- 扫描到已带"执行中" label 的 issue 直接跳过，避免重复认领。
- **一次 run 只认领一个 issue**。批量开发属于外部编排的事，不是单个 run 的职责。

### 3.3 远端确认门（remote-gate）——能力 A 的核心机制

**问题**：原有确认门靠"本地对话等待用户回复"。改为 Issue 驱动后，人是在 GitHub 上审核的，流水线必须能"停下来、等一个来自 GitHub 的信号、之后再继续"。

**思路**：把确认门做成一个**幂等、可重入**的原子任务。第一次进入时把产物推给 issue、打审核 label、暂停并持久化状态；之后任何一次恢复，都先重入这个门、读取 GitHub 信号，决定放行还是否决。这样完全复用现有"状态文件 + 恢复"机制，不引入新执行器。

**参考解法**（门任务的执行逻辑）：
1. 首次进入（状态文件里没有该门的待决记录）：
   - 把本阶段产物的摘要评论到 issue；
   - 打"待审核:<阶段>" label；
   - 写入待决门记录，把 run 置为"等待远端门"状态，持久化后结束会话。
2. 恢复时重入（已有待决记录），读取远端信号：
   - 命中"已批准" → 摘审核 label，记录通过事件，放行下一节点；
   - 命中"要求修改" → 读取白名单作者的最新评论作为反馈，走现有"带反馈重生"逻辑；
   - 两者都没有 → 判超时。超时按策略处理（评论催办 / 挂起 / 终止），未超时则继续等待。
3. 超时阈值与动作做成可配置参数，默认建议 72 小时后挂起。

**配套**：运行时需新增"等待远端门"状态与对应恢复规则（恢复时优先重入待决门），并在执行历史中新增三类远端门事件（待决 / 通过 / 否决）。

**授权与防注入**：读取"要求修改"的反馈评论时，只接受授权作者白名单内的作者。label 管控制，comment 管数据，二者职责严格分离。

### 3.4 loop 自检（轮次可配置）

**问题**：coding、verification 这类节点希望 AI 先自查自纠若干轮，再交人工，且轮次要可配。

**思路**：复用原子任务既有的"可配置参数（options）"机制表达轮次，loop 行为写进任务指令。不为此发明新的结构。

**参考解法**：
- 给 coding 增加"自检最大轮次"参数，给 verification 增加"最大重试次数"参数。
- 指令约定：执行后自动跑测试 / 静态检查，失败则自行修复并重试，直到通过或达到轮次上限。
- 运行状态记录当前轮次，执行历史增加"循环迭代"事件，保证可审计。
- 超过上限 → 打"失败" label，评论卡点原因，转人工。

这与现有"verification 失败回到 coding 重做"同构，本质是把"重试次数"参数化并加上界。

### 3.5 交付与 PR 闭环

**问题**：回归通过后要产出报告与交付文档，并创建 PR，在 GitHub 上闭环。

**参考解法**：
- 报告阶段产出执行报告（沿用既有能力）。
- 增加"交付文档"节点：按既有归档模板机制汇总，内容为需求回溯（issue → 功能需求 → 验收标准 → 验证结果）、变更清单、风险说明。
- 增加"创建 PR"节点：推送特性分支，创建 **draft PR**，正文包含关闭 issue 的引用、执行摘要、产物链接、验证结论；同时在 issue 评论 PR 链接，并把 label 置为"完成"。
- **合并永远由人执行**。draft PR + 人工合并是 autopilot 的最后一道安全阀。

所有产物文档随特性分支一并提交，PR 页面即可直接查看，交付物就是 PR 本身。

### 3.6 状态检查 / Watcher：如何及时感知信号

**问题**：门暂停后，如何及时知道人已经打了批准 label？

**思路**：GitHub 对 issue/PR 没有公开推送通道，本质只能轮询。分两层：**已知在等某个门**就专注盯它；**没有明确等待对象**就周期巡检。并按执行 agent 的能力做适配。

**参考解法**：
- 等待具体某个门：用监听机制跑一个 gh 轮询脚本，查询 label / PR 状态，状态变化即唤醒 agent，命中终态信号即退出并续跑流水线。
- 多 run 巡检：用自定节奏的循环任务，扫描"新的触发 issue"与"信号已就绪的等待中 run"。
- 跨会话存活：会话内的轮询都随会话死亡。要无人值守，靠操作系统定时任务拉起 headless agent 巡检。但由于状态已持久化，**任何时候手动开一个会话恢复，也同样能推进**——watcher 从来不是必需品。
- 轮询间隔建议不低于 30 秒，脚本需容忍瞬时失败（失败不退出、下轮重试）。

### 3.7 触发入口的取舍

**问题**：新 issue 打 label 后，能否自动拉起流水线？

**结论**：本期只做"会话内显式触发"（用户指明用 issue 驱动工作流处理某 issue）。webhook / CI 自动触发需要能访问本地 worktree 的 runner，属于后续增强，见 §6。这样避免误触发，也避免引入常驻基建。

## 4. 能力 B：节点级模型路由

### 4.1 核心认知：主会话不能换模型，subagent 可以

**问题**：希望不同原子任务用不同模型。

**关键事实**：Claude Code 主会话的模型无法被程序化切换（只能用户手动操作）。但 **subagent 委派是原生能力，且每次委派都能指定模型**。因此"按节点切模型"的正确实现是：**把该节点委派给一个指定模型的 subagent 执行**，而不是让主会话变身。

**职责切割**：skill 只负责选择"模型值"；这个值最终落到哪个真实模型，由环境配置（端点映射 / 网关）决定，skill 不感知、也不应感知。

### 4.2 模型值的表达与优先级

**思路**：模型值做成开放字符串，取两类值之一——**档位别名**，或**完整模型名**。

**参考解法**：
- 模型配置分三层：原子任务自带默认值；全局用户覆盖；工作流级用户覆盖。优先级从高到低为"工作流覆盖 > 全局覆盖 > 任务默认 > 继承主会话"。
- 值为"继承"或未配置 → 节点在主会话内联执行（行为与现状完全一致，保证向后兼容）。
- 该配置项应视为保留键，与"启用/禁用"同级，不参与普通 options 合并。

### 4.3 两种模型值的触发路径（重要差异）

**档位别名**（如 opus / sonnet / haiku / fable）：
- 委派 subagent 时，把别名直接作为"本次调用的模型参数"传入即可。
- 别名如何落到真实模型，由环境的档位映射决定（见 §5.1 已验证事实）。

**完整模型名**（如某个中继上的具体模型标识）：
- 本环境的"每次调用模型参数"只接受档位别名，**完整模型名必须写进 subagent 定义文件的 model 字段，再按名委派**。
- 运行时按需生成/复用这样的 subagent 定义，把配置里的模型名填入其 model 字段。

**收尾**：subagent 按原子任务指令执行、产物落盘后，父会话验证产物存在再推进，并在运行状态中记录"实际使用的模型"，供审计与未来成本归因。确认门仍由父会话主持，subagent 不与用户交互；运行状态由父会话统一写入。

### 4.4 别名是封闭集合（交接必知）

**档位别名不可新增**。想接入别名体系之外的模型，一律走"完整模型名直通"路径（§4.3）。不要试图扩展别名，那是客户端内置词汇，改不了。

### 4.5 多模型并行评审（review 扇出）

**问题**：评审阶段想用多个模型交叉评审。

**参考解法**：
- 给评审任务一个"模型列表"参数（多个模型值）。
- 指令约定：按列表逐个委派 subagent 独立评审；每个 subagent 只回结论级摘要（避免大量中间输出灌回主会话）；父会话合并为一份评审报告。
- 模型数量不受限，取决于网关上注册了多少模型。

## 5. 多模型与密钥：网关聚合

### 5.1 单会话单凭证的硬约束

一次 Claude Code 会话只有**一组凭证**：一个端点 + 一把 key。委派 subagent 时的模型参数只改变请求体里的模型名，**不改变端点与凭证**。

推论：
- 要让不同节点用不同供应商的模型，必须有一个"按模型名路由"的统一端点——即 **LLM 网关**。
- 想绕开网关、让节点直连不同供应商，原生做不到；只能退化为"外部执行器"路子（用 Bash 调自带 key 的第三方编码 CLI），不推荐作为主路径。
- 如果所有模型都是官方 Claude 档位，则无需网关，原生开箱即用。

### 5.2 密钥的分层管理

**参考解法**：
- 本地部署一个 LLM 网关，注册 N 个模型，每个模型映射到真实供应商与真实 key。
- Claude Code 侧只配一把 key：端点指向网关，认证用网关凭证。
- 各供应商的真实 key 全部下沉到网关配置，**不进 Claude Code、不进代码仓库**。
- 仓库内的任何配置只允许出现模型名，绝不出现密钥。

### 5.3 配置工具的立场：不依赖 cc-switch

**结论**：能力 B 不依赖 cc-switch。
- 官方配置面（环境变量 / 设置的 env 块 / 动态取 key 脚本）足以完成全部配置，一次性、量小。
- cc-switch 只是"多供应商 profile 一键切换"的便捷层；在固定一套网关配置的场景下收益很小，且它**不提供模型聚合**。
- 交接文档与用户指南应以官方配置为规范路径，cc-switch 仅作为可选提及。理由：社区工具可能停更、接口漂移，不应成为用户的前置安装假设。

唯一绕不开的依赖是网关本身（仅多模型场景需要）。

## 6. 关键决策与取舍（交接重点）

| 决策点 | 选择 | 理由 |
|---|---|---|
| 控制信号载体 | label，非 comment | 授权内置、防注入 |
| 确认门形态 | 远端门 + 状态持久化 + 恢复 | 契合指令型 runtime，不占会话、可中断 |
| 触发方式 | label + 显式指定工作流 | 避免关键词误触发 |
| 模型后端 | 网关聚合，非多端点直连 | 受单会话单凭证约束 |
| 配置工具 | 官方 env 为规范，cc-switch 为可选 | 稳定、可移植、不绑社区工具 |
| 交付方式 | draft PR + 人工合并 | autopilot 的最后安全阀 |
| 模型词汇 | 四档位别名 + 完整名直通 | 别名为封闭集合，不可扩展 |
| 交付文档 | 复用既有归档模板机制 | 不发明新机制 |
| 监听机制 | 轮询，分层 + 按 agent 适配 | 无公开推送通道；watcher 仅为加速器 |

## 7. 环境约束与前置检查（接手方必须确认）

1. 具备 gh CLI 与目标仓库的访问权限；打 label 需 triage 及以上权限。
2. 中继 / 网关端点可用，目标模型已在网关注册。
3. **确认未设置"全局 subagent 模型覆盖"环境变量**——它一旦存在会覆盖所有按节点的模型路由。
4. **确认模型白名单（如有）未排除目标模型**——被排除的模型会静默回退为继承，不报错。
5. 执行 agent 需支持 subagent 委派（Claude Code）。其他宿主降级为内联执行并输出警告，功能可用但无模型切换。
6. 跨会话无人值守依赖操作系统定时任务 + headless agent，属可选增强。

## 8. 已验证事实（实施基础，非假设）

1. 本环境端点指向一个中继，四个档位已分别映射到自定义模型（分属不同供应商）。
2. 实测：委派 subagent 传入某档位别名，实际由该档位映射的自定义模型执行，链路全程打通。
3. 当前未设置全局 subagent 模型覆盖变量，按节点路由的控制权完整。
4. 本环境"每次调用模型参数"仅接受档位别名；完整模型名须经 subagent 定义文件传入。
5. 档位别名为封闭集合，不可新增。

## 9. 风险与边界

| 风险 | 级别 | 缓解 |
|---|---|---|
| issue 撰写质量差导致下游跑偏 | 中 | 认领时做需求完整性检查，缺关键信息则暂停 |
| 远端门授权与注入 | 高 | 控制信号仅认 label；反馈评论限白名单作者 |
| 单 run 误认领多 issue | 低 | 认领任务强制单 issue |
| subagent 上下文隔离导致交接缺失 | 中 | 交接内容自包含：任务全文 + 方案引用 + 文件路径 + 验收锚点 |
| 全局模型覆盖变量干扰路由 | 中 | 实施前置检查确认未设置 |
| 模型白名单静默回退 | 中 | 实施前置检查确认目标模型在列 |
| gh 鉴权 / 网络失败 | 低 | 失败即终止并明确报错 |
| 网关不可用 | 低 | 模型路由失败回退继承，记录警告，不中断流水线 |

## 10. 建议实施顺序（按能力单元）

| 阶段 | 能力单元 | 说明 |
|---|---|---|
| 1 | label 协议 + 认领 + issue 驱动工作流骨架 | 先打通"issue → 认领 → 执行"通道，确认可用本地确认门 |
| 2 | 远端确认门 + 运行时恢复协议 | 能力 A 的核心，依赖阶段 1 |
| 3 | loop 自检（轮次可配） | 可与主线并行 |
| 4 | 交付文档 + 创建 PR + 状态监听 | 依赖阶段 2 |
| 5 | 节点级模型路由 + 网关密钥指南 + 评审扇出 | 可与主线并行 |
| 6 | 全流程演练 | 用一个真实 issue 走完整链路验收 |

后续增强（本期不做）：CI/webhook 自动触发、反向建 issue、多 issue 并行编排、按节点的成本归因。

## 11. 交接备注

- 本文档刻意不绑定具体文件与路径，以便接手者按当前代码结构自行落位。落位时请遵循现有约定：原子任务以独立目录承载、工作流以独立定义承载、运行时规则集中在 skill 主体、用户可配置项集中在覆盖机制里。
- 能力 A 与能力 B 相互独立，可分别排期；二者交汇仅在 coding 与 review 节点。
