## 对齐摘要

- 用户目标：把 ddo 流水线的**启动相关状态机**一次性设计定版并稳定下来——每次启动的询问内容一致，存在运行中 run 时有快速 resume 通道。
- 期望交付：①统一且不漂移的启动引导（修 issue #64 症状一）②coding 结束确认门：同意/提问/修改（修症状二）③快速 resume + 启动标准重设计 ④`.claude/settings.local.json` 从仓库追踪排除。
- 关键边界：3、4 本质同源（启动标准问题）；确认门用项目既有 gate 机制承载；`.gitignore` 变更已经用户在冷启动明确授权并入本次 PR。
- 当前状态：BQ-1 已由用户决议——形态 (b) 协议+结构层（CLI `guide` payload 扩展为启动检查单一数据源，SKILL.md 只引用不自述）；spec 已按答案写回，等待用户批准。

## 用户目标

- 启动相关的状态机本次设计好，要保证稳定性——每次启动时询问的内容一致、时序确定。
- 仓库内存在执行中的工作流时，提供快速 resume 的方式。
- coding 执行完后不得静默跑完工作流：补用户确认阶段，选项为 同意、提问、修改。
- `.claude/settings.local.json` 从仓库中排除。

---

## 范围与非目标

### In Scope

- 启动状态机统一设计：触发 → 运行中 run 检查（resume 优先呈现）→ 引导问询（固定问题序列）→ worktree 场景确认 → 启动登记 的确定性时序，及其在 SKILL.md 的单一权威描述。
- SKILL.md 提示部分的全面回归：消除冷启动/resume/worktree 问询的多源描述与顺序漂移（issue #64 症状一）。
- coding 阶段结束确认门：选项 同意 / 提问 / 修改。
- `.gitignore` 追加 `.claude/settings.local.json`（同类本地运行时产物的具体集合留给 Planning）。

### Non-goals

- 不重设计确认门机制本身（gate present / interact / decision 既有结构不动，只做挂接与选项定制）。
- 不改原子任务的执行内核（exec/validate/next 节律）。
- 不处理 2026-09-30 全项目质量检查报告（issue #62）中的其他发现——本次只做用户列出的 4 项。

## 约束与保留术语

- 保留用户术语：`启动状态机`、`确认阶段`（映射到项目既有机制 `确认门 gate`）、`快速 resume`、`询问的内容是一致的`。
- 项目事实约束：skill 硬边界——运行期不写 skillRoot、不擅改 `.gitignore`；本次 `.gitignore` 变更为用户明确授权的流水线变更项（走 PR 审查）。
- 项目事实约束：确认门已有结构化支持（`gate present` 留痕、未呈现不决议、in-phase 交互后须重新呈现）——coding 门应复用该机制而非新造交互协议。
