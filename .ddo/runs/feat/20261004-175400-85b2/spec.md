# 多仓库 worktree 隔离目录模式 Spec

> 本文档用于确认 agent 是否正确理解用户关于「支持多仓库变更的 worktree 隔离目录模式」的需求。

---

## 对齐摘要

- 用户目标：ddo-code-flow 支持一次 run 同时修改多个仓库（服务）的场景。
- 期望交付：新增「多 worktree 隔离目录」模式——启动时可选；选中后先建隔离容器目录（根放 `.ddo`，其下并列各仓库的 worktree 子目录），state 的 `git` 段与 `dirs` 升级为多仓库表达；交付链（deliver-pr / closeout-worktree 等）同步适配多仓库。
- 关键边界：与现有单仓库模式完美兼容，不选新模式时行为完全不变。
- 设计期望：方案要让整体逻辑更好——自洽融入现有机制，不做生硬叠加。
- 当前状态：BQ-1～BQ-3 已解决并写回，等待用户批准。

---

## 用户目标

- 工作流能覆盖一次需求需同时修改多个仓库文件的场景。
- 以「多 worktree 隔离目录」容器隔离本次需求的多个 worktree 分支。
- 启动时由用户选择本次流程是否采用该隔离模式。
- state 如实升级：`git` 段表达多仓库、`dirs` 表达多个项目目录。
- 整体逻辑更优：设计自洽，兼容性不受损。

---

## 范围与非目标

### In Scope

- 新增多 worktree 隔离目录模式：容器目录（根含 `.ddo`）+ 容器内各仓库独立 worktree。
- 启动问询接入「是否采用隔离模式」选择项。
- 采用时由 agent 提出候选仓库清单，经用户确认/修订后据此建容器与各 worktree。
- state 的 `git` 段与 `dirs` 升级为多仓库语义，并对既有单仓库 state 保持兼容。
- 执行链路（任务/相位/门）对多仓库工作目录的兼容。
- 交付链（deliver-pr / closeout-worktree 等）适配多仓库：逐仓库 PR 与清理。

### Non-goals

- 不改变现有单仓库模式的任何行为（完美兼容是硬边界）。
- 不在用户确认前自动纳入任何仓库。
- 不支持运行中途追加仓库（BQ-1 已确认启动确认制）。
- spec 层不定实现细节（schema 字段命名、CLI 参数形态、命名算法）——留给 Planning。

## 约束与保留术语

- 保留术语：「多 worktree 隔离目录」（隔离容器）；`project-1` / `project-2`（用户示例的仓库子目录形态）；`.ddo`；state 的 `git` 段、`dirs`。
- 术语映射：用户原文中「服务」与「仓库」同义使用，spec 统一用「仓库」。
- 用户约束：完美兼容现有单仓库模式——兼容性优先，变更大不构成破坏兼容的理由。
- 用户约束：设计需让整体逻辑更好——与现有 worktree/状态/任务机制自洽协调，不做生硬叠加。
