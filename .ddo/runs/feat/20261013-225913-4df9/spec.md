# 测试工作流与依赖检查能力 Spec

> 本文档用于确认 agent 是否正确理解用户关于「为 ddo-code-flow 新增测试工作流与原子任务依赖检查能力」的需求。

---

## 对齐摘要

- 用户目标：为 ddo-code-flow 新增一条测试工作流（测试范围设定 → 测试计划制定 → 单测/接口/e2e 分级执行），并新增原子任务依赖检查能力。
- 期望交付：可配置启停的测试工作流（含标准范围确认文档、分层计划与测试报告），以及依赖声明 + 本机依赖检查 + 结果驱动的动态询问机制。
- 关键边界：三类测试职责受明确约束——单测保证代码基础能力、接口测试保证 req/resp 符合预期并能调通、e2e 保证功能；单个测试的能力范围不过大。
- 当前状态：BQ-1 已按用户答复写回（以目标 + 阶段 + 关联代码变更界定范围），等待用户批准。

---

## 用户目标

- 新增测试工作流：测试范围设定 → 测试计划制定（各子模块可配置启停）→ 单元/接口/e2e 测试执行（各产出测试报告）。
- 新增依赖检查能力：原子任务可声明所需依赖并给出检查脚本，依次检查本机支持情况，并据此动态调整用户询问。

---

## 范围与非目标

### In Scope

- 测试范围设定：来源二选一——用户输入信息设定范围，或读取项目中 /ddo-code-flow 存在的 .state.json 作为范围；设定后产出一份标准的测试范围确认文档（不多也不少）。
- 测试计划制定：总测试设计（整体说明）+ 单元测试计划 / 接口测试计划 / e2e 测试计划；每类可 config 配置是否开启，流程启动时提示用户选择启用哪些测试能力计划。
- 单元测试计划启用时：提示配置测试性能优先（串行，每次执行 1-3 条）或效率优先（并行）。
- e2e 测试计划启用时：选择产出人工 e2e 测试指南，或直接通过工具能力自动化测试；后者须对本机依赖进行前置检查。
- 单元 / 接口 / e2e 执行阶段（若配置）：检查对应测试计划 → 执行测试计划 → 产出测试报告。
- 依赖检查能力：原子任务声明依赖 + 依赖检查脚本 + 依次检查本机是否支持 + 动态询问（缺依赖时提示是否同意下载三方依赖启用该能力；非强制依赖时提示可不下载、使用基础能力）。

### Non-goals

- 不为单测/接口/e2e 增加用户未要求的覆盖率门槛、性能指标等验收项。
- 不突破三类测试的既定职责边界（不把接口级或 e2e 级验证塞进单测等）。
- 不擅自改动用户未提及的现有工作流语义或其他既有能力。

## 约束与保留术语

- 保留用户术语：测试范围设定、总测试设计、单元测试计划 / 接口测试计划 / e2e 测试计划、测试性能优先[串行每次执行 1-3 条] / 效率优先[并行]、人工 e2e 测试指南、依赖检查能力、原子任务、req/resp、「不多也不少」。
- 「不多也不少」= 范围确认文档所列范围与所设定范围严格一致，无遗漏、无扩写。

## 解释与假设

| 类型 | 内容 | 依据或原因 | 若错误的影响 |
|---|---|---|---|
| Interpretation | 「新增测试工作流」指为 ddo-code-flow 系统本身新增一条独立可选的测试工作流（阶段顺序：范围设定 → 计划制定 → 分级执行），不改动既有其他工作流的语义。 | 用户描述的是一条自洽完整的流程，且提出位置在本系统项目内。 | 若用户意图是嵌入现有工作流作为可选段，交付的工作流形态会不同。 |
| Interpretation | 「项目中 /ddo-code-flow 存在的 .state.json」指项目内 ddo 运行状态文件；存在多份或不存在时，通过问询让用户选定具体文件或改用用户输入来源。 | 对范围来源选项的最小可操作解释。 | 多份/缺失场景的实际行为可能与用户预期不同，可在确认时一并指正。 |
| Assumption | e2e 选「人工指南」形态时，e2e 执行阶段的产出为人工 e2e 测试指南文档（供人工执行）；选「自动化」形态时产出自动化测试报告。 | 用户为 e2e 计划给出两种产出形态，执行阶段标注 [同上]（产出报告）。 | 若人工形态也要求执行后的测试报告，e2e 阶段的产物定义会不同。 |
