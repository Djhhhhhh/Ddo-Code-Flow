# 用户需求

> 用户触发此流水线的原始需求描述。

## 原始需求

新增测试工作流，执行流程如下：

1. 测试范围设定：
    - 测试范围提供选项如下：
        - 用户输入信息，设定测试范围
        - 读取项目中 /ddo-code-flow 存在的 .state.json，作为范围
    - 测试范围设定后产出一份标准的测试范围确认文档，保证不多也不少

2. 测试计划制定（每个测试的子模块均可以通过config配置是否开启，并且在启动该流程的时候提示用户需要启用哪些测试能力计划）：
    - 总测试设计（用于整体说明）
    - 单元测试计划（若后续节点配置需要进行单测，可提示用户配置测试性能优先[ 串行每次执行1-3条 ]还是效率优先[ 并行 ]）
    - 接口测试计划（若后续节点配置需要进行接口测试）
    - e2e测试计划（若后续节点配置需要进行e2e测试，并且提供选择是产出人工e2e测试指南，还是直接通过工具能力自动化测试，！需要对本机的依赖进行前置检查）

    注意：每个步骤的计划理论上是服务于对应的功能的，单测保证代码基础能力，api保证 req、resp符合预期并能调通、e2e保证功能，不要单个测试的能力范围过大

3. 单元测试（若配置）
    - 检查单元测试计划，执行测试计划，产出测试报告

4. 接口测试（若配置）
    - [ 同上 ]

5. e2e测试（若配置）
    - [ 同上 ]

补充：新增依赖检查能力，原子任务可以说明自己需要什么依赖，并且给出依赖检查脚本，依次检查机器是否支持该能力，然后根据依赖能力是否支持，动态调整用户询问，如：缺少了依赖，就提示用户是否同意下载三方依赖，使用原子任务的该能力；若原子任务非强制依赖特别能力，则提示用户可不下载对应的依赖使用基础能力。

## 需求摘要

新增覆盖测试范围设定、分层测试计划制定与单测/接口/e2e 分级执行的测试工作流，并为原子任务增加依赖声明与本机依赖检查能力。
