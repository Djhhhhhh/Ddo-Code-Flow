# test-design

> 测试工作流计划阶段：总测试设计（整体说明）+ 按启用能力的分层测试计划。计划服务于对应功能：单测保证代码基础能力、接口保证 req/resp 符合预期并能调通、e2e 保证功能。

<!-- @phase:01 -->
## 制定分层测试计划

<!-- @interact:required tool=ask-user -->
本相位包含必须完成的交互（按启用能力触发：单测执行模式问询 / e2e 形态选择 / 依赖缺失问询），未完成前不得调用任何推进命令，也不得产出计划文档。
<!-- /interact -->

1. 读取 Context 中的测试范围确认文档与启用能力清单（state.atomTasks.test-design.capabilities）。
2. 生成 `## 总测试设计`：范围概览、分层策略、各层职责边界声明（单测=代码基础能力、接口=req/resp 预期且能调通、e2e=功能）。
3. 按启用能力逐层生成计划（section 标题固定，未启用层级不出现在文档中）：
   - **## 单元测试计划**（启用 unit 时）：先经宿主提问工具问询执行模式——**测试性能优先**（串行，每次执行 1-3 条）或**效率优先**（并行）；计划含用例清单（每条对应范围条目内的代码基础能力）与所选模式。
   - **## 接口测试计划**（启用 api 时）：接口清单，每项含 req 预期、resp 断言与调通目标。
   - **## e2e 测试计划**（启用 e2e 时）：先经宿主提问工具问询产出形态——**人工 e2e 测试指南** 或 **通过工具能力自动化测试**。选自动化时必须先执行本机依赖前置检查：
     `node tools/cli.js deps check --state <statePath> --task test-e2e`
     按结果经宿主提问工具问询：缺失且 required=true → 询问是否同意按 install 指引下载三方依赖以启用该能力（用户同意则安装后复查，拒绝则建议改人工指南形态）；缺失且 required=false → 提示可不下载、使用基础能力（改人工指南形态）。计划记录所选形态、依赖检查结论与问询结果。
4. 在 `## 启用能力` 列出本次启用清单（unit/api/e2e 的子集）。
5. 写入 run 目录 `test-design.md`。
<!-- /phase:01 -->

<!-- @phase:02 -->
## 确认门

<!-- @interact:required tool=ask-user -->
必须调用宿主提问工具向用户请求确认，未获得用户明确回复前不得调用任何推进命令。
<!-- /interact -->

向用户展示计划摘要（启用能力、各层用例规模、单测模式、e2e 形态与依赖检查结论）。

**门选项从统一呈现入口获取**：跑 `node tools/cli.js gate present --state <statePath>` 取交互 payload（本门全部选项的 name/desc/dispatch），把各选项原样呈现给用户（宿主提问工具），不得在 payload 之外自造选项。用户选择后按 dispatch 处理：
- 命令型（`next --decision <name>` / `rollback --stage …`）→ agent 代跑 dispatch 命令；
- 相位内交互（`in-phase`）→ 先 `gate interact --state <statePath> --option <name> [--note <摘要>]` 记录交互，再按下方行为定义处理；处理完成后**重新 `gate present` 送审**——未重新呈现前的决议会被结构拦截。

相位内交互行为定义：

- `修改：<反馈>`：按反馈更新受影响条目（含重新问询模式/形态/依赖），展示变化摘要后重新送审；
- `提问：<问题>`：只答疑，不修改产物、不改变确认状态。
<!-- /phase:02 -->
