# spec

> 生成唯一标准的 Alignment Spec，让用户能够审查 agent 对需求的理解，发现遗漏、误解和无依据扩写，并在进入 Planning 前明确批准。

**总约束**（两相位通用）：

- spec 只描述用户要什么、为什么需要、如何判断理解正确；不得提前选择库、框架、内部文件路径或实现算法。
- 用户明确要求的外部接口、数据格式或兼容边界属于需求可以保留；agent 自行选择的实现细节留给 Planning。
- 不得把 agent 推断、常识或项目惯例伪装成用户明确要求。
- 保留用户原始术语；需要规范化时同时给出映射，不得静默改名。
- FR、AC、BQ 的 ID 在修订中保持稳定；仅删除被明确替代的条目。
- 条件 section 没有真实内容时必须省略，不得用「无」「待定」填充版面。

## 生成 Alignment Spec

### 1. 建立对齐证据

按以下优先级读取和处理证据，低优先级内容不得覆盖高优先级内容：

1. 当前会话中用户最新、明确的纠正或决定；
2. Context: Requirement 中持久化的用户原始需求；
3. Context: Context Summary 中可定位的项目事实；
4. agent 明确标注的解释或假设。

Requirement 缺失时停止生成并指出缺失，不得依赖模型记忆重建原始需求。Context Summary 缺失时允许继续，但不得补写仓库事实、文件结构或技术约束。

提取用户目标、期望交付、范围、非目标、明确约束、保留术语和成功条件，将候选内容分类为：

- **Explicit**：用户明确表达的要求或决定；
- **Context Fact**：项目上下文中可定位的事实；
- **Interpretation**：对明确要求的等价规整或解释，必须说明依据；
- **Assumption**：证据不足时采用的暂定理解，必须说明错误时的影响；
- **Conflict**：用户要求、用户修订或项目事实之间无法同时成立的内容。

### 2. 使用唯一 Alignment Spec 标准

所有需求都生成同一种 Alignment Spec。不得创建 Minimal、Standard、Clarification-First 等等级，也不得使用 profile、mode、overlay 或模板选择算法。简单需求只缩短各 section 内容；高歧义需求仍用同一结构，通过「需要用户确认」和批准状态表达风险。

生成的 spec 至少包含：对齐摘要、用户目标、范围与非目标、需求对齐（FR 列表）、成功结果（AC 列表）、用户确认；约束与保留术语、解释与假设、需要用户确认（BQ）、留给 Planning 仅在有真实内容时出现。

需求对齐中的每个 FR 必须：使用稳定 ID；只表达一个主要义务；让用户能够判断 agent 的理解是否正确；标明来源或解释类别；关联一个或多个用户可观察的成功结果——若只是背景，不得伪装成 FR。

### 3. 判断风险与阻塞问题

- **阻塞风险（BQ）**：存在多种合理解释，且不同答案会改变用户目标、交付物、范围、明确约束或成功结果。使用稳定 BQ ID 写入「需要用户确认」，解决并写回前不得批准。
- **非阻塞风险**：低影响未知用 Interpretation 或 Assumption 明示并说明影响；不得把推断写成已确认要求。
- **Planning 决策**：只影响实现方式、不改变 What/Why 的技术选择，写入「留给 Planning」，不得用它阻塞需求批准。

一个问题成为 BQ 的必要条件：现有证据没有唯一答案；不同答案会改变交付结果；保守收窄范围仍无法避免猜测；用户可以作出具体决定。不得为满足模板强制制造开放问题。

### 4. 生成成功结果

优先使用用户明确给出的成功条件。只有能够从要求等价推导时，才可添加最小的用户可观察结果，并标记为 Interpretation。不得凭专业常识擅自增加性能、安全、兼容性、持久化等非功能验收项。每个 AC 必须列出其验证的 FR。

### 5. 输出前自检

逐项检查并修正：Coverage（重要明确要求都有落点）、No invention（FR/约束/AC 都有来源或显式标注）、Terminology（术语未偷换）、Scope（In/Out 不冲突不扩）、Atomicity（一 FR 一义务）、Observable outcome（AC 可判成败）、Question necessity（每个 BQ 说明影响）、Conciseness（删空 section 与凑版内容）、Revision stability（未受影响的 ID 与语义稳定）。

自检通过后，将 spec 写入 run 目录的 `spec.md`。

## 确认门

<!-- @interact:required tool=ask-user -->
必须调用宿主提问工具（如 Claude Code 的 AskUserQuestion）向用户请求确认，不得以自由文本代替，未获得用户明确回复前不得调用任何推进命令。
<!-- /interact -->

向用户展示 spec 摘要与关键决策点，按当前状态提供动作：

- 不存在未解决 BQ 时：提供 `同意`、`修改：<反馈>`、`提问：<问题>`；
- 存在未解决 BQ 时：不得提供可批准状态，改为提供 `回答 BQ-N：<答案>`、`修改：<反馈>`、`提问：<问题>`。

动作语义：

- `同意`：仅当不存在未解决 BQ 时批准当前 spec，本相位完成；
- `回答 BQ-N：<答案>`：把答案作为最高优先级的最新显式用户决定写回 spec，更新所有受影响内容（目标、范围、FR、AC、约束、术语、解释/假设、BQ 状态），将对齐变化摘要展示给用户并重新请求确认；BQ 答案不得等价为批准；
- `修改：<反馈>`：把反馈作为新的需求证据，仅更新受影响条目并保留其他稳定 ID，展示变化摘要后再次请求确认；
- `提问：<问题>`：只读答疑，不修改 spec、不改变任何 ID 与确认状态；若答案暴露问题，仅解释影响并询问是否需要 `修改：...`。

用户明确驳回 spec 本身时：执行 `rollback --stage spec --reason <用户意见>`，随后按驳回意见回到相位 01 重新生成。
