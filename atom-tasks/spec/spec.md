# spec

> 生成唯一标准的 Alignment Spec，让用户能够审查 agent 对需求的理解，发现遗漏、误解和无依据扩写，并在进入 Planning 前明确批准。

## 指令

### 1. 建立对齐证据

按以下优先级读取和处理证据，低优先级内容不得覆盖高优先级内容：

1. 当前会话中用户最新、明确的纠正或决定；
2. `{{inputs.requirement}}` 中持久化的用户原始需求；
3. `{{inputs.context-summary}}` 中可定位的项目事实；
4. agent 明确标注的解释或假设。

requirement 角色缺失时停止生成并指出缺失，不得依赖模型记忆重建原始需求。context-summary 角色缺失或为空时允许继续，但不得补写仓库事实、文件结构或技术约束。

提取用户目标、期望交付、范围、非目标、明确约束、保留术语和成功条件。将候选内容分类为：

- **Explicit**：用户明确表达的要求或决定；
- **Context Fact**：项目上下文中可定位的事实；
- **Interpretation**：对明确要求的等价规整或解释，必须说明依据；
- **Assumption**：证据不足时采用的暂定理解，必须说明错误时的影响；
- **Conflict**：用户要求、用户修订或项目事实之间无法同时成立的内容。

### 2. 使用唯一 Alignment Spec 标准

所有需求都生成同一种 Alignment Spec。不得创建 Minimal、Standard、Clarification-First 等等级，也不得使用 profile、mode、overlay 或模板选择算法。简单需求只缩短各 section 的内容；高歧义需求仍使用同一结构，通过“需要用户确认”和批准状态表达风险。

按 `spec.output.schema.json` 生成：对齐摘要、用户目标、范围与非目标、需求对齐、成功结果和用户确认是 Alignment Core；约束与保留术语、解释与假设、需要用户确认、留给 Planning 仅在有真实内容时出现；对齐变化摘要仅在发生写回修改后的 revision 中出现。

需求对齐中的每个 FR 必须：

- 使用稳定 ID；
- 只表达一个主要义务；
- 让用户能够判断 agent 的理解是否正确；
- 标明来源或解释类别；
- 关联一个或多个用户可观察的成功结果；若只是背景，不得伪装成 FR。

### 3. 判断风险与阻塞问题

风险分级只决定“是否需要澄清、当前能否批准”，不决定生成等级：

- **阻塞风险**：存在多种合理解释，且不同答案会改变用户目标、交付物、范围、明确约束或成功结果。使用稳定 BQ ID 写入“需要用户确认”，解决并写回前不得批准。
- **非阻塞风险**：低影响未知可以用 Interpretation 或 Assumption 明示，并说明影响；不得把推断写成已确认要求。
- **Planning 决策**：只影响实现方式、不改变 What/Why 的技术选择，写入“留给 Planning”，不得用它阻塞需求批准。

一个问题只有同时满足以下条件才可成为 BQ：现有证据没有唯一答案；不同答案会改变交付结果；保守收窄范围仍无法避免猜测；用户可以作出具体决定。不得为了满足模板强制制造开放问题。

### 4. 生成成功结果

优先使用用户明确给出的成功条件。只有能够从要求等价推导时，才可添加最小的用户可观察结果，并标记为 Interpretation。不得凭专业常识擅自增加性能、安全、兼容性、持久化或其他非功能验收项。每个 AC 必须列出其验证的 FR；行为示例仅在自然语言存在多种行为解释时使用。

### 5. 执行 Fidelity Self-Check

输出前逐项检查并修正：

- **Coverage**：每项重要的用户明确要求都有对应位置；
- **No invention**：每项 FR、约束和 AC 都有来源或显式 Interpretation/Assumption；
- **Terminology**：保留用户领域术语，规范化表达没有偷换含义；
- **Scope**：In Scope 与 Non-goals 不冲突，也未凭空扩大；
- **Atomicity**：每项 FR 只表达一个主要义务；
- **Observable outcome**：AC 可由用户判断成功或失败；
- **Question necessity**：每个 BQ 都说明不同答案会改变什么；
- **Conciseness**：删除空 section、重复解释和只为匹配模板存在的内容；
- **Revision stability**：未受反馈影响的 ID 和语义保持稳定；
- **Confirmation integrity**：只有显式写回动作（`修改：...` 或 `回答 BQ-N：...`）才修改文档；`提问：...` 不改变文档或状态。

### 6. 修订与确认分流

用户确认 section 按当前状态提供动作：

- 不存在未解决 BQ 时：提供 `同意`、`修改：<反馈>`、`提问：<问题>`；
- 存在未解决 BQ 时：不得提供可批准状态，改为提供 `回答 BQ-N：<答案>`、`修改：<反馈>`、`提问：<问题>`。

动作语义固定如下：

- `同意`：仅当不存在未解决 BQ 时批准当前 spec，并进入 Planning；
- `回答 BQ-N：<答案>`：把答案作为最新的显式用户需求证据写回，更新所有受影响的对齐内容，包括目标、范围、FR、AC、约束、术语、解释/假设和 BQ 状态；展示对齐变化摘要并重新请求确认；BQ 答案不得等价为批准；
- `修改：<反馈>`：把反馈作为新的需求证据，更新受影响内容，展示对齐变化摘要，再次请求明确确认；
- `提问：<问题>`：仅回答问题，不修改 spec，不改变 FR/AC/BQ ID、revision、确认状态或 history 中的修订记录。

处理 `回答 BQ-N：` 时：

1. 将答案作为优先级最高的最新显式用户决定；
2. 更新所有受该答案影响的对齐内容，包括目标、范围、FR、AC、约束、术语、解释/假设和 BQ 状态，并保持其他内容与稳定 ID 不变；
3. 将对应 BQ 标记为已解决并从未解决问题中移除；
4. 在对齐变化摘要中列出修改项和已解决问题；
5. 重新请求用户确认，不得把 BQ 答案视为 `同意`。

处理 `提问：` 时：

1. 即使内容暗含修改，也只答疑；
2. 若是真实问题，回答后询问：“是否需要根据上述说明修改 spec？如需，请使用 `修改：...`。”；
3. 若实际是修改命令，不执行修改，提示用户改用 `修改：...`；
4. 若答案暴露遗漏、冲突或错误，只解释影响并询问是否修改，收到明确修改指令前保持 spec 原样。

处理 `修改：` 时，仅更新受反馈影响的条目，保留其他稳定 ID，列出新增、修改、删除和已解决问题。修订完成后重新展示三种动作；修改选择、问题回答或 BQ 答案都不能等价为批准。

## 约束

- spec 只描述用户要什么、为什么需要以及如何判断理解正确；不得提前选择库、框架、内部文件路径或实现算法。
- 用户明确要求的外部接口、数据格式或兼容边界属于需求，可以保留；agent 自行选择的实现细节必须留给 Planning。
- 只能生成一个 Alignment Spec 标准；不得输出生成等级、profile、mode 或模板名称。
- 不得把 agent 推断、常识或项目惯例伪装成用户明确要求。
- 保留用户原始术语；需要规范化时同时给出映射，不得静默改名。
- FR、AC、BQ 和 Planning Decision 的 ID 在修订中保持稳定；仅删除被明确替代的条目。
- 条件 section 没有真实内容时必须省略，不得使用“无”“待定”填充版面。
- 存在未解决 BQ 或 Conflict 时不得提供可批准状态。
- 用户必须明确选择 `同意` 才能批准；任何其他回复不得视为隐式同意。
- `提问` 永远是只读答疑动作；答疑内容没有后续明确的 `修改：...` 就不得写回 spec。`回答 BQ-N：...` 是独立的显式需求决定，应按 BQ 写回流程处理。
