# coding

> 按任务清单（或 plan 实施步骤）执行真实代码改动。产物是代码变更本身，不是文档。

<!-- @phase:01 -->
## 执行模式

**任务清单模式**：若 Context 中存在 tasks（task 清单与 task-NN.md），解析拓扑关系并按批次执行——存在并行分组则每个内部数组是一个批次，按顺序执行；否则按 dependsOn 拓扑排序，同层任务归为一个批次。逐个执行 task-NN.md 所述编辑，在 state 中为对应 task 写入一行完成标记。不得跳过任务，不得编造任务。批次开始前，若批次内每个任务都已标记完成，视为无操作跳过。

**直执行模式**（任务清单不存在时，如轻量工作流）：读取 Context 中的 Alignment Spec 与 Plan，将 plan 的实施步骤按依赖顺序作为任务执行，并在 state 中记录每一步结果。test-plan 在该模式下也是可选输入，不得仅因其缺失而中止。

**验证修复模式**：若上一轮验证失败（存在失败检查项记录），只处理失败项关联的任务或实施步骤：将这些条目从 done 重新打开为 pending，记录本轮修复原因和轮次，修复完成后再进入后续验证。不得因为任务曾经标记 done 就跳过失败修复。

## 自检循环

默认至多 3 轮（可通过 rules/extra_ctx 调整）：执行编码 → 运行项目测试与静态检查（如有）→ 全部通过则结束；否则自行修复失败项并记录轮次到 state（供审计）。超过最大轮次仍有失败：暂停并等待人工介入，说明失败原因。

## 约束

- 仅在「Context: 工作目录」声明的生效目录内创建/修改文件，不得操作该目录之外的任何路径。
- 保留无关文件；做最小化、有针对性的编辑。
- 任务失败时，在 state 中记录失败，仅在通知用户后继续后续批次中的独立任务。
- 从 Context 注入的任务清单读取任务，不要从 run 目录顶层猜测任务位置。

## 完成确认门

<!-- @interact:required tool=ask-user -->
必须调用宿主提问工具向用户请求确认，未获得明确回复前不得调用任何推进命令。
<!-- /interact -->

coding 的代码改动完成、进入工作流后续阶段（reporting / verification 等）之前，必须经用户确认——不得静默推进。

**门选项从统一呈现入口获取**：跑 `node tools/cli.js gate present --state <statePath>` 取交互 payload（本门全部选项的 name/desc/dispatch），把各选项原样呈现给用户（宿主提问工具），不得在 payload 之外自造选项。用户选择后按 dispatch 处理：
- 命令型（`next --decision 同意`）→ agent 代跑 dispatch 命令，放行后续阶段；
- 相位内交互（`in-phase`）→ 先 `gate interact --state <statePath> --option <name> [--note <摘要>]` 记录交互，再按下方行为定义处理；处理完成后**重新 `gate present` 送审**——未重新呈现前的决议会被结构拦截（重新询问由结构强制，不靠自觉）。

相位内交互行为定义：

- `同意`：确认 coding 产物完成，本相位完成并放行后续阶段；
- `提问：<问题>`：对实现内容答疑（只读说明，不动代码）；
- `修改：<反馈>`：按反馈调整**相位 01 的代码变更本身**（无产物归档动作——`_del` 机制属 rollback，不属门内修改），完成后重新送审。
