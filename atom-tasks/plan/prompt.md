# plan

> 基于已确认的 spec 生成指导开发的技术 Plan：技术决策、实现边界、仓库复用契约与下游交接。用户确认后方可进入后续编排。

**总约束**：面向本地仓库实现工作，只描述当前仓库/组件及直接依赖的外部契约；不生成人员分工与排期；不负责测试计划（只提供 Verification Anchor）；所有输出写入 state `git.worktreePath` 指向的工作树。

<!-- @phase:01 -->
## 生成 Plan

### 1. 建立仓库事实

读取 Context 中的 Alignment Spec（已确认）；Context Summary 存在则读。在 worktree 中检查与需求直接相关的现有设计：公共类/函数/共享组件与扩展点、请求响应/分页/错误处理标准、schema/DDL/迁移/缓存/日志约定、相似业务流程与目录布局。每项影响设计的结论进入「现有设计与复用基线」，记录能力说明、文件路径、符号、证据类型、采用方式与适用边界。

- 证据类型仅允许：`Repository Fact`（已读真实文件且可定位符号）、`Assumption`（证据不足，须写明待确认方式）；
- 采用方式仅允许：`复用现有实现`、`扩展现有实现`、`新增实现`、`不适用`；选新增必须说明现有能力为何不满足；
- 有条件复用原则：满足需求/兼容/质量时 复用 > 扩展 > 新增；废弃或不匹配的实现不得机械复用。

### 2. 形成技术决策

先写需求范围、非目标与约束，再写复用基线。「技术选型与方案对比」按真实候选生成（不凑数）：候选来源为初始发现与用户补充，状态用 `candidate`/`accepted`/`rejected`/`superseded`，只保留关键差异、仓库适配性、代价、风险与结论。每个重大 Decision 写明结论、依据、权衡、影响范围与回退条件。spec 中每个开放问题给出唯一确定答案；无法安全确定时保留为阻塞项并请求澄清，不得伪造。

### 3. 详细设计（按适用性，无改动的写简短不适用原因）

1. **数据模型**：实体、字段、类型、约束、关系、状态流转、索引；确有数据库变更才给 schema/DDL 与迁移策略（含兼容、回滚、不变量）。
2. **API 接口**：引用已定义数据模型，优先复用仓库现有请求/响应/分页/鉴权/错误/幂等标准；描述方法、路径、请求、响应、错误语义与兼容边界；不另造平行协议。
3. **算法**：仅非平凡算法/状态机/并发/一致性逻辑才写：输入输出、不变量、关键步骤、复杂度、边界。普通业务逻辑不写伪代码与逐行清单（那是 Coding 职责）。
4. **流程与交付边界**：只为直接相关的主/异常流程生成 Mermaid 流程图（禁 PlantUML/ASCII 图）；按适用性描述兼容/性能/安全/可观测/灰度/回滚；文件变更计划只到「文件职责 + 契约」粒度。

### 4. 组织文档（single / split）

先在内存形成完整逻辑草稿并按 Unicode code point 计数。阈值默认 12000（最小 4000，配置非法则停止并报告）：

- `<= 阈值`（single）：完整内容写入 plan.md，标记模式 `single`，不创建 plans/；
- `> 阈值`（split）：plan.md 保留标题、revision、执行摘要、核心决策、追踪总览、Parts Manifest、读取协议与确认命令；详细内容按语义边界写 `plans/NN-<semantic-slug>.md`（编号连续）；manifest 记录文档、职责、字符数、状态与 AI 索引，有效分册标 `current`；不得在表格/Mermaid/Decision/schema 中间硬切；新 revision 重写 manifest，旧分册标 `stale` 不得被下游读取。

### 5. 下游交接与归档

- 下游验收/拆分从 plan.md 出发，按 manifest 读 current parts；Coding 按 task 加载相关 part，证据失效时停止报告，不得自行改已批准契约；
- `归档`：枚举 `atom-tasks/plan/references/` 下 `*.md` 模板名（不生成）；`归档：<模板名>` 按名精确匹配生成/刷新 tech-design 产物（记录模板名与来源 revision）；归档不是批准，不改变确认状态，revision 变化即失效。

### 6. 静态检查

每个 revision 写完后执行**一次**内联检查：frontmatter/JSON 引用可解析、标题层级/链接/manifest 与 current parts 一致、代码与 Mermaid 围栏闭合、split 计数与编号、必需章节与开放问题映射。失败报告不自动重试；等用户 `修改` 后下一 revision 再查一次。

自检通过后将 Plan 写入 run 目录 `plan.md`（split 模式含 plans/）。

## 确认门

<!-- @interact:required tool=ask-user -->
必须调用宿主提问工具向用户请求确认，未获得明确回复前不得调用任何推进命令。
<!-- /interact -->

向用户展示 plan.md 路径、文档模式（single/split）、revision、分册数与静态检查结果，提供动作：

- `同意`：批准当前 revision，本相位完成；
- `修改：<反馈>`：反馈应用到新 revision（补充的候选方案加入同一集合并重评估），展示变化摘要后再次请求确认；
- `提问：<问题>`：只答疑，不改文档、revision 与确认状态；
- `归档` / `归档：<模板名>`：见相位 01 §5；不代表批准。

用户明确驳回 Plan 本身时：执行 `rollback --stage plan --reason <用户意见>`，随后按意见回到相位 01 重新生成。
